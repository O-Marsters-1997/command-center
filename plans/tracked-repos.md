# Plan: tracked repos

> Source: `docs/prds/prd-tracked-repos.md` (PRD Phase 1 only), prototype variant C on
> `prototype/tracked-repos` (`eb5c27e`), `CONTEXT.md` § **Repo** and § **Track**.
> Label: project:tracked-repos

Untrack and deleting a checkout are PRD Phase 2 and are not planned here.

## Technical design decisions

### Settled in planning (2026-10-05)

- **A settings file that stops parsing refuses the repo, and it heals on its own.** The loop
  re-reads `.command-centre.toml` from `origin/main` on every tick, so merging the fix returns the
  repo to `ready` with no verb. Last-good settings are never kept.
- **A refused repo is retried with the same Track.** The `stop` banner carries Track again. GitHub
  check refusals (merge settings, default branch, clone) are re-evaluated only on Track. Settings
  refusals are re-evaluated every tick, as above.
- **A repo's page lists the features its own tracker offers.** When an imported feature also holds
  tickets in other repos, the row names those repos in a muted note.
- **The board is scoped from the banner.** The repo page's banner carries a `board →` link to
  `/?repo=owner/name`. `cc open` keeps working.
- **The model stays daemon-wide.** A per-repo model override in `.command-centre.toml` is deferred.
- **The handler writes no `repos` row.** `repos` is reconciled state, so the loop is its only writer
  (ADR 16). `POST /repos/track` queues an intent and nothing else, and the page renders `cloning`
  from the pending intent until the loop has written the row. This corrects the PRD's sequence
  diagram, which shows the handler inserting the row.

### Routes

| Route | Shape | Notes |
| --- | --- | --- |
| `GET /features` | unscoped: the repos page | Search box over the tracked-repos table. Replaces today's unscoped feature list. |
| `GET /features?repo=owner/name` | scoped: the repo page | Small search box, title, remote, state banner, features table. `owner/name` validates against tracked repos *and* against pending track intents; an unknown name renders the `not tracked` banner rather than an error. |
| `GET /features/search?q=` | htmx fragment | `hx-get` from the search box, `hx-trigger="input changed delay:300ms"`, swaps the table body. An empty `q` returns the tracked-repos table. |
| `GET /features/banner?repo=owner/name` | htmx fragment | The banner on its own. It polls every 2s (`hx-trigger="every 2s"`) only while it renders `cloning`, and sends `HX-Refresh: true` when the state changes so the features table appears. |
| `POST /repos/track` | form `repo=owner/name` | Queues a `track` intent and redirects (or htmx-swaps) to the scoped page. It does no git or GitHub work. It is idempotent: a second Track while one is pending queues nothing. |

`owner/name` travels as a query value, never as a path segment, so its `/` needs no escaping
scheme. The import route `POST /features/{feature}/import` and the board's `?repo=` are unchanged
in shape; only the values become `owner/name`.

### Schema

Migration `0010_repos.sql`:

```sql
CREATE TABLE repos (
    name             text PRIMARY KEY,          -- owner/name, GitHub full name
    remote           text NOT NULL,             -- git URL cloned from
    state            text NOT NULL,             -- cloning | ready | refused
    refusal_kind     text,                      -- merge_settings | default_branch | clone | settings_parse
    refusal          text,                      -- human sentence naming what to fix
    settings_source  text,                      -- file | defaults; NULL until first read
    settings_read_at timestamptz,
    tracked_at       timestamptz NOT NULL,
    CHECK (state IN ('cloning', 'ready', 'refused')),
    CHECK ((state = 'refused') = (refusal IS NOT NULL))
);
```

- **Parsed settings are not stored.** They are read from `origin/main` each tick and held in the
  tick's repo set. The table records only where they came from and when, which is all the banner
  shows.
- **`intents` is unchanged.** A `track` intent puts `owner/name` in `ticket_id`, following the
  `import` intent, which already puts a feature name there. Renaming the column to `target` is
  worthwhile but out of scope.
- **`tickets.repo` is rewritten in Go, not SQL.** The owner comes from the `[[repo]]` remote, which a
  goose file cannot see. The first-boot import rewrites it in the same transaction that inserts the
  `repos` rows (Phase 3).
- **Persisted observations under old keys need no migration.** They were keyed by
  `branchKey(shortName, branch)`, so they read as a tick that observed nothing, exactly as the
  board-scope plan's key change did.
- Queries live in a new `internal/cc/queries/repos.sql` and are generated by sqlc (ADR 8).

### Key models

- **`RepoSettings`** holds every per-repo key that `[[repo]]` holds today: `Tracker`, `Stacking`,
  `Deny`, `Checks`, `CompatCheck`, `MergifySHA`, `VerifyCommand`, `Generated`, `BuildCommand`.
  It is decoded from `.command-centre.toml` with the same TOML tags `[[repo]]` uses today, so
  moving a block is a cut and paste. Its zero value is "defaults", except `Tracker`, which defaults
  to `github` as `LoadConfig` does now.
  - `compat_check` and `mergify_sha` are per-repo too, although the PRD's key list leaves them out.
    The config describes only the daemon (decision 8), so both move into the file.
- **`Repo`** becomes the repo's identity plus its settings: `Name` (`owner/name`), `Remote`,
  `Checkout` (derived as `<data_dir>/repos/<owner>/<name>`, never stored), `State`, and an embedded
  `RepoSettings`. Embedding keeps every `r.Stacking` and `r.Deny` read compiling, so the ten
  `…ByRepo` index helpers in `config.go` survive unchanged. `Path` is deleted.
- **`Config`** keeps only the daemon keys: `port`, `data_dir`, `database_url`,
  `claude_projects_dir`, `agent_command`, `max_turns`, `max_agents` and `spend_limit_5h`.
  `Repos []Repo` is replaced by `LegacyRepos []legacyRepo` (`toml:"repo"`), which only the
  first-boot import reads.
- **`RepoState`** is a string type with three values, `cloning`, `ready` and `refused`. Each maps
  to a tone and a pill glyph as the prototype does:

  | State | Tone | Glyph |
  | --- | --- | --- |
  | not tracked | `idle` | `pill-ring` |
  | `cloning` | `live` | `pill-pulse` |
  | `refused` | `stop` | `pill-ring` |
  | `ready` | `done` | `pill-disc` |

  The mapping lives in Go as tone words. The template composes the classes, and Go never returns a
  utility string.

### Module boundaries

- **`internal/cc/reposettings.go`** is a deep module behind one call: `ReadRepoSettings(ctx,
  checkout) (RepoSettings, source, error)`. It runs `git show origin/main:.command-centre.toml`.
  A missing path answers defaults with source `defaults`. A parse error, an unknown key
  (`toml.MetaData.Undecoded`) or an invalid predicate answers an error that names the line. Test
  it in isolation against a temporary repo.
- **`internal/plan`** gains `.command-centre.toml` in `defaultDeny`. That is a fact about every repo
  and needs no settings to enforce, so an agent cannot remove it through the file itself.
- **The loop owns the repo set.** At the start of each tick it reads `store.Repos(ctx)`, reads
  settings for every repo with a checkout, and builds the tick's `[]Repo`. Every current
  `l.cfg.Repos` read becomes a read of that per-tick slice (`l.repos`, set once per tick, since the
  loop is single-goroutine). Steps that act — launch, push, refresh, generated-conflict, draft gate,
  verbs, merge events — see only `ready` repos.
- **The observer covers every repo with a checkout**, `ready` or `refused`. A repo refused by
  `settings_parse` still has in-flight tickets, and the board must stay honest about them while
  nothing new launches or pushes there. A repo refused before cloning has no checkout and is not
  observed. One repo's fetch failure no longer fails the tick: it is recorded against that repo,
  and the other repos are still observed.
- **The repo checks live in `internal/cc/repocheck.go`.** `checkRepoSquashOnly` is generalised to
  `checkRepoOnGitHub(ctx, owner/name) (refusal_kind, reason, error)`. It reads
  `gh api repos/{owner}/{name} --jq '{allow_merge_commit, allow_rebase_merge, default_branch}'`
  by explicit name rather than a checkout's `{owner}/{repo}` placeholder, so it runs before
  cloning. `AssertReposSquashOnly` and the startup gate are deleted.
- **`internal/gh`** gains `PushableRepos(ctx) ([]RepoSummary, error)`.
  - It calls `gh api --paginate user/repos?affiliation=owner,collaborator,organization_member&per_page=100`,
    filtered to `.permissions.push == true`.
  - `RepoSummary` carries `FullName`, `SSHURL`, `DefaultBranch` and `Archived`.
  - It needs no checkout, so it takes no `repoPath`.
- **The server caches `PushableRepos` in memory for 60s.** A keystroke must not trigger a paginated
  API walk, so the server filters the cached list by case-insensitive substring of `FullName`. This
  is a read in a handler, like today's `ImportFeatures`, and is allowed under ADR 16.
- **The server reads repos from the store** (`store.Repos`) for the breadcrumb, the repos table,
  `?repo=` validation and the scoped features list. `NewServer` loses its `repos []Repo` parameter.
- **`cc open`** opens the store from the config's `database_url`, as `cc useradd` already does, and
  matches the working directory's origin against `repos.remote` with the existing `sameRemote`.

### Key flows

**Track (loop, one intent per tick step):**

1. The loop reads a pending `track` intent for `owner/name`.
2. It upserts `repos(name, remote, state='cloning', tracked_at)`. The remote is the SSH URL from
   `gh api repos/{owner}/{name}`.
3. It runs `checkRepoOnGitHub`. A failure sets `refused` with `merge_settings` or `default_branch`
   and consumes the intent. The default-branch reason reads: "default branch is `master`, not
   `main`; rename it on GitHub, then Track again."
4. `EnsureCheckout` at `repos/<owner>/<name>` clones the repo, or fetches it and verifies origin. A
   failure sets `refused` with `clone`.
5. `ReadRepoSettings` runs. A failure sets `refused` with `settings_parse`.
6. The repo becomes `ready`, with `settings_source` and `settings_read_at` written, and the intent
   is consumed.

Steps 3 to 5 are the same function the loop runs for imported repos in Phase 4. Track on a
`refused` repo re-runs the whole flow. Track on a `ready` repo is a no-op.

**Per tick, for each tracked repo with a checkout:** the loop fetches, reads the settings and
writes the state.

- `ready` with a parse error becomes `refused(settings_parse)`.
- `refused(settings_parse)` with a clean read becomes `ready`.
- Every other refusal kind is left alone until Track.

**First boot (`App.New`, after the flock, before the loop):**

- If the `repos` table is empty and the config has `[[repo]]` blocks, the app imports them in one
  transaction:
  - It derives `owner/name` from each remote (`normaliseRemote`) and inserts a `cloning` row.
  - It rewrites `tickets.repo` from the short name to `owner/name`.
  - On disk, if `repos/<short>` exists and `repos/<owner>/<name>` does not, it moves the checkout
    to the new path and leaves a symlink at the old path, so treepad worktrees' recorded absolute
    paths keep resolving (the ADR 5 fix).
- If the `repos` table is non-empty and the config still has `[[repo]]`, the app refuses to start:
  "cc/config.toml still has [[repo]] blocks; repos are tracked in the database now — delete them."
- Otherwise the app starts with zero or more repos. No repo check runs at startup.

### Integration points

- **GitHub through `gh`.** `user/repos` for search, `repos/{owner}/{name}` for the checks, and the
  existing `gh pr list` and issue calls per checkout. All of them run as the box's single `gh`
  identity.
- **git.** `git show origin/main:.command-centre.toml` after each fetch, plus clone and fetch
  through `EnsureCheckout`.
- **Postgres.** The `repos` table and `track` intents.

### Auth

Unchanged. Every page and verb already sits behind the session middleware (`auth.go`). Search and
Track act as the box's `gh` identity whoever is logged in; the repos page says so in one muted line
under the search box.

### Styling

- The repos table and banner use the existing state grammar: `banner ribbon` with `data-tone`, and
  `pill` with its glyph classes.
- Layout and spacing come from template utilities. No new colour tokens are needed, because the
  states map onto the existing tones.
- `just assets` must run, and the rebuilt `internal/cc/assets/dist/app.css` must be committed, in
  every phase that touches a template.
- Never remove or rename an `hx-` attribute, `id="board"` or the `hx-preserve` detail row.

### Human-only steps

- **Deleting `[[repo]]` from `cc/config.toml`** after the first-boot import (end of Phase 3). The
  file is not deny-listed, so an agent can open that PR, but the daemon restart that follows is a
  human act.
- **The laptop symlink is created by the first-boot import,** not by hand. A human should check
  `tp list` afterwards.
- **No phase touches `.github/**`, `go.mod`, `go.sum` or `.golangci.yml`.** No new Go dependency
  is needed, because `BurntSushi/toml` is already in `go.mod`.

## Phase 1: the ADR and this repo's settings file

**User stories**: guardrails are reviewed in the repo they guard; an agent cannot loosen its own
guardrails.

### What to build

- **The ADR** (`docs/adr/0021-repos-are-tracked-not-configured.md`). It records that:
  - repos live in Postgres and are tracked from the page;
  - per-repo settings live in `.command-centre.toml` on the target's `origin/main`, with the file's
    own path always denied;
  - `path` is dropped and repos are named `owner/name`;
  - the config describes only the daemon.

  It supersedes the relevant parts of ADR 3 and ADR 5, and those two get a "partly superseded by
  ADR 21" status line. `CONTEXT.md`'s already-drafted **Repo** and **Track** entries land in the
  same PR.
- **`.command-centre.toml` committed at this repo's root.** It carries today's command-center block
  verbatim: `stacking`, `deny`, `generated`, `build_command` and `checks`. Nothing reads it yet. It
  must be on `origin/main` before Phase 2 ships, or command-center's deny list silently disappears.
- **`plan.defaultDeny` gains `.command-centre.toml`**, with a `plan` test showing that a push
  touching it is refused.

### Acceptance criteria

- [ ] ADR 21 is merged, and ADR 3 and ADR 5 carry a status line pointing to it.
- [ ] `.command-centre.toml` on `main` decodes into today's command-center `[[repo]]` values (a test
      decodes both and compares).
- [ ] An agent push that changes `.command-centre.toml` is refused by the push policy in every repo,
      whatever that repo's own `deny` says.

## Phase 2: settings read from `origin/main`

**User stories**: Scenario "tightening what agents may touch"; settings change only through a PR
you merge.

### What to build

- Introduce `RepoSettings` and `ReadRepoSettings`. After the observer fetches each repo, the loop
  reads the file from `origin/main` and overlays it onto the repo, still identified by its config
  block.
- `[[repo]]` keeps `name`, `remote` and `path` for now. A per-repo key left in a `[[repo]]` block
  becomes a startup error naming the key and pointing to `.command-centre.toml`.
- There is no `repos` table yet, so a parse error is recorded as the tick's last error. That repo is
  skipped for every act step that tick: no launch, push or refresh in it.

### Acceptance criteria

- [ ] With this repo's settings file on `main` and `[[repo]]` stripped to name and remote, the
      daemon pushes, verifies and resolves generated conflicts exactly as before. The golden files
      do not change.
- [ ] Merging a change to `deny` in `.command-centre.toml` takes effect on the next tick with no
      restart. Covered by a loop test that swaps the file on a fake origin.
- [ ] A missing file yields zero-value settings (tracker `github`).
- [ ] A malformed or unknown-key file skips act steps for that repo and surfaces in the masthead's
      last error.
- [ ] Settings are never read from a ticket's branch or worktree, even when the ticket's branch
      carries a different `.command-centre.toml`. A test covers this.

## Phase 3: the `repos` table and `owner/name` identity

**User stories**: repos are identified by `owner/name`; the config describes only the daemon; first
boot imports `[[repo]]` once; `cc open` resolves against tracked repos.

### What to build

- **Migration `0010_repos.sql`** and the `repos.sql` queries (`Repos`, `UpsertRepo`,
  `SetRepoState`).
- **The first-boot import** described in Key flows: rows go in as `ready`, since Phase 4 hasn't
  moved validation yet; `tickets.repo` is rewritten; the checkout moves with a symlink; and a later
  boot that still finds `[[repo]]` is refused.
- **`Config.Repos` and `Path` are removed.** `LoadConfig` no longer resolves checkouts.
- **The loop builds its per-tick repo set** from `store.Repos` plus settings, and every
  `l.cfg.Repos` read moves to it. The startup squash check runs over the store's repos for now.
- **`NewServer` drops its `repos` parameter.** The breadcrumb's `RepoLinks` and `?repo=` validation
  read the store. The switcher stays for now; Phase 6 removes it.
- **`cc open`** reads tracked repos from the store.
- **A follow-up PR** deletes `[[repo]]` from `cc/config.toml`, and the human restarts the daemon.

### Acceptance criteria

- [ ] A fresh database plus today's `cc/config.toml` boots once, and afterwards `repos` holds
      `O-Marsters-1997/command-center` and every ticket's `repo` reads the same.
- [ ] The checkout is at `repos/O-Marsters-1997/command-center`, `repos/command-center` is a
      symlink to it, and `tp list` in an existing worktree still works.
- [ ] A second boot with `[[repo]]` still present is refused with the "delete them" message. A boot
      without it starts normally.
- [ ] `/?repo=O-Marsters-1997/command-center` scopes the board, and `cc open` from a checkout opens
      that URL.
- [ ] `grep -rn 'cfg.Repos' --include='*.go'` returns nothing.
- [ ] The golden files are regenerated, and their diff shows only `owner/name` where the short name
      was.

## Phase 4: validation moves into the loop

**User stories**: Scenario "a repo that can't be driven yet"; one bad repo no longer stops the
daemon.

### What to build

- Delete the startup repo checks (`ensureAllCheckouts`, `AssertReposSquashOnly`) and their `App`
  options.
- The first-boot import now inserts rows as `cloning`. A shared `validateRepo` (Key flows, steps 3
  to 5) carries each one to `ready` or `refused(kind, reason)` on the loop's first tick.
- The per-tick settings read drives `ready` ↔ `refused(settings_parse)` as described in Key flows.
- The observer covers `ready` and `refused` repos with checkouts; act steps take `ready` repos
  only.
- A per-repo fetch failure is recorded against that repo and no longer fails the tick.
- The board needs no new UI in this phase. A refused repo's reason shows through the existing
  last-error surface until Phase 5's banner exists.

### Acceptance criteria

- [ ] The daemon starts with zero repos, and with a repo that allows merge commits; in the latter
      case only that repo is `refused(merge_settings)`.
- [ ] A repo whose default branch is `master` is `refused(default_branch)` with the rename hint, and
      is never cloned.
- [ ] Breaking `.command-centre.toml` on a ready repo turns it `refused(settings_parse)` within one
      tick: its in-flight tickets stay visible, and none launches or pushes. Fixing the file returns
      it to `ready` with no verb.
- [ ] One repo's fetch failure leaves every other repo reconciling that tick.

## Phase 5: Track from the scoped repo page

**User stories**: Scenario "starting on a new project from your phone" (reached by URL until
Phase 6); the repo page's title, banner and Track; features listed from the repo's own tracker;
a board link in the banner.

### What to build

**The track verb.** `POST /repos/track` queues a `track` intent. `applyTrackIntents` runs the Key
flows track sequence on the loop.

**The scoped `/features?repo=owner/name` page** shows:

- a small search box (inert until Phase 6);
- `owner/name` as the title, with the remote under it;
- the banner fragment;
- the features table.

**The banner states:**

| State | Banner text |
| --- | --- |
| not tracked | `idle` banner: "Not tracked. Tracking clones it, checks it, and reads .command-centre.toml from main." Track sits inside the banner. |
| `cloning` (row or pending intent) | `live` banner naming the step in progress. It polls `/features/banner` and refreshes the page on change. |
| `ready` | `done` banner: "Reconciling. Settings from .command-centre.toml on main." or "…defaults are in use.", plus the `board →` link. |
| `refused` | `stop` banner: the reason, plus Track. |

The four check steps from the prototype (clone, squash-only, default branch, settings file) render
as a small step list derived from `state` and `refusal_kind`.

**The features table** lists the features from this repo's tracker only (`ImportFeatures` over the
one repo). An imported feature whose tickets also sit in other repos names them in a muted note.
Import and launch from here are unchanged.

### Acceptance criteria

- [ ] On `/features?repo=owner/new`, pressing Track shows `cloning` straight away, and the handler
      issues no `git` or `gh` command. A test asserts this with a recording runner.
- [ ] A few ticks later the banner reads `ready` (with "defaults are in use" when there is no file),
      and the repo's features appear without a manual reload.
- [ ] Track on a `refused` repo re-runs validation. Track twice while one is pending queues one
      intent.
- [ ] The `board →` link lands on `/?repo=owner/name`.
- [ ] A feature that spans repos shows its other repos on each repo's page.
- [ ] There are new golden files for each banner state, and `app.css` is rebuilt and committed.

## Phase 6: the repos page and search

**User stories**: Finding a repo; search covers repos the box can push to; the breadcrumb becomes
plain links.

### What to build

- **`gh.PushableRepos` and its 60s server cache.**
- **Unscoped `/features` becomes the repos page.**
  - It has a large search box and the tracked-repos table: name, state pill, and either the refusal
    reason or the settings source.
  - Typing swaps in `/features/search?q=`, which merges the pushable repos with tracked state.
  - An untracked match shows `not tracked` with a `track →` link to its scoped page.
  - Archived repos are excluded.
- **The scoped page's small search box goes live** with the same fragment.
- **The breadcrumb becomes plain links** reading workspace / repos / `owner/name`. `#repo-switcher`,
  its popover script in `layout.tmpl`, `RepoLinks` and `repoLinksFor` are deleted, along with the
  `repo-switcher` CSS.

### Acceptance criteria

- [ ] An empty query lists exactly the tracked repos, with their states.
- [ ] Typing `api` lists the pushable repos matching `api`, with tracked ones showing their state.
      A repo the box can only read never appears. A `gh` fake covers this.
- [ ] Repeated keystrokes within 60s make one `gh` call.
- [ ] The breadcrumb has no popover. Each segment is a link, and the `owner/name` segment appears
      only when scoped.
- [ ] Golden files are regenerated for the repos page and both search states, and `app.css` is
      rebuilt and committed.

## Phase 7: nice-to-haves

**User stories**: PRD Phase 1 ✨ items.

### What to build

- **The masthead raises any `refused` repo** the way it raises the last error, linking to that
  repo's page. It stays visible while the board is scoped to another repo.
- **Search rows show `default_branch`** from `RepoSummary`. A non-`main` branch marks the row "will
  be refused: default branch is `master`" before Track. Merge settings are not in `user/repos`, so
  they are not shown pre-Track; fetching them per row would mean one API call per result.

### Acceptance criteria

- [ ] A refused repo shows in the masthead on every page until it is `ready` again.
- [ ] A `master`-default repo is visibly marked in search results, and Track still works on it,
      ending in `refused(default_branch)`.
