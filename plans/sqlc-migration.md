# Plan: the sqlc migration

> Source: the `Next` card in `ideas/roadmap.html`. Both of its open questions were settled in a
> grilling session on 2026-09-13, recorded in `docs/adr/0008-sql-is-generated-from-the-schema.md`.
> No PRD; this plan is the design document.

## The starting point

The store makes 36 hand-written SQL calls, which become 39 named queries once `DeleteTicket`'s
four-statement loop is unrolled:

| file | call sites | named queries |
| --- | --- | --- |
| `internal/cc/store.go` | 8 | 11 |
| `internal/cc/runs.go` | 13 | 13 |
| `internal/cc/launch.go` | 9 | 9 |
| `internal/cc/pushes.go` | 5 | 5 |
| `internal/cc/refresh.go` | 1 | 1 |

Every one of them is a string. Nothing checks it against the schema until it runs, and the first
sign of a mistake is a failed tick.

The schema is not static. Migration 0002 renamed `tasks` to `tickets` and renamed the foreign key
column in five tables. Migration 0003 added six columns to `tickets`, and because SQLite refuses
`NOT NULL` on `ALTER TABLE ADD COLUMN` without a default, all six are nullable and every read
`COALESCE`s them back to empty strings. A hand-written statement gets that kind of change wrong
quietly.

It already has. `events.ticket_id` is nullable and `launch.go:135` writes `NULL` into it on
purpose, for a launch event belonging to no single ticket. Both `latestRefreshOutcomes`
(`refresh.go:61`) and `RestackedTickets` (`pushes.go:30`) scan that column into a plain `string`.
Neither has failed, because each one's `kind` filter happens to exclude launch events. Add a sixth
kind to the refresh filter, or start recording a launch under a kind those filters match, and both
panic on a NULL. Nothing in the code says the filter is load-bearing.

## What the spike proved

sqlc's SQLite engine is beta. That is a reason to check before committing, not a reason to walk
away, so I ran sqlc v1.31.1 against the real migrations and the six hardest queries in the store
before writing any of this down.

- **The goose migrations replay.** sqlc reads `internal/cc/migrations` directly, understands the
  `-- +goose Up` annotations, and applies 0002's `ALTER TABLE tasks RENAME TO tickets` and its five
  `RENAME COLUMN`s. The generated model is `Ticket` with a `URL` field. There is no stale `Task`.
- **The window function types.** `COUNT(*) OVER (PARTITION BY lm.launch_id)` in `LaunchMemberships`
  comes out as `Members int64`.
- **`COALESCE` types cleanly.** `COALESCE(source, '')` generates `Source string`, not
  `interface{}`. The six accidentally-nullable `tickets` columns cost nothing.
- **`sqlc.slice()` works on this engine.** It matters for `refresh.go`, below.
- **`rename:` reaches both models and per-query row structs.**
- **golangci-lint never sees the generated package.** v2's `linters.exclusions.generated` defaults
  to `strict`, and sqlc's `// Code generated by sqlc. DO NOT EDIT.` header matches it exactly.
  `golangci-lint run` over the generated code reports no issues, so neither staticcheck's
  initialism rule nor `lll` applies to it.

## What does not change

**The schema.** This migration adds no migration of its own. Other work will: phase 8 of
`plans/repo-and-ticket-model.md` adds `0004_withdrawal.sql`, and sqlc reads whatever
`internal/cc/migrations` holds, so landing either order is fine. The six nullable `tickets` columns
keep their `COALESCE`. The nullable columns on `runs` stay nullable
because NULL is load-bearing there: `WHERE pgid IS NOT NULL AND outcome IS NULL` is the predicate
for a run that is still alive, and `RunSummary` already models it with `*int` and `*time.Time`.

**`Store`'s public API.** Every method keeps its signature, its domain types, its JSON decoding of
`blocked_by`, its RFC3339 parsing and its error wrapping. `Tickets()` still returns
`fmt.Errorf("select tickets: %w", err)`. The generated `Queries` becomes an unexported field, and
nothing outside `internal/cc` sees `sql.NullString` or a generated row struct.

**`Store.db`.** goose needs `*sql.DB` for migrations and the transactional methods need it for
`BeginTx`, so it stays. That is also the escape hatch: a query the beta parser rejects stays
hand-written on `s.db` beside the generated ones, for as long as it needs to.

## The shape

```
internal/cc/
├── migrations/          0001_init.sql, 0002_tickets.sql, 0003_ticket_fields.sql
├── queries/             store.sql, runs.sql, launch.sql, pushes.sql, refresh.sql
└── ccdb/                generated, committed
    ├── db.go
    ├── models.go
    └── <name>.sql.go    one per queries/<name>.sql
```

One `.sql` per Go file, so each phase below adds exactly one `.sql` and one generated `.go`, and
finding the SQL behind a method is the same lookup it is today.

`sqlc.yaml` at the repo root:

```yaml
version: "2"
sql:
  - engine: "sqlite"
    schema: "internal/cc/migrations"
    queries: "internal/cc/queries"
    gen:
      go:
        package: "ccdb"
        out: "internal/cc/ccdb"
        rename:
          url: "URL"
          baseline_sha: "BaselineSHA"
          base_sha_at_push: "BaseSHAAtPush"
```

Those three are the only columns whose generated names disagree with the domain structs. Without
the block they arrive as `Url`, `BaselineSha` and `BaseShaAtPush` next to a `Ticket.URL` and a
`PushRow.BaseSHAAtPush`.

Drift is caught the way the repo already catches it for `app.css` and `go.mod`:

```
# Justfile
sqlc:
    go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1 generate
```

and a CI job that runs `just sqlc` then `git diff --exit-code internal/cc/ccdb`. The version is
pinned in the `go run` line rather than added to `go.mod`, which would drag pgx, wazero, the TiDB
parser, cel-go and grpc into a 70-line `go.sum` for a tool that never ships in the binary.

## Phase 0: the board's columns are renamed

Not a sqlc change, and it touches no file the other phases touch, so it can land whenever. It is
here because the decision behind it had to be made before phase 1: sqlc derives every generated
identifier from the table and column names, and the term was contradicting itself.

`CONTEXT.md` defined **task** as the unit of work and listed **ticket** under *Avoid*. The schema,
the Go code and 298 identifiers said `Ticket`. The board said both: a `ticket` column holding the
tracker reference `#CC-1`, and a `task` column holding the title and reason. So `Ticket` meant the
work in Go and the tracker's reference in the UI.

Resolved: **ticket** is the work, at every layer. The `#CC-1` column is headed **ref**.

`board.tmpl` changes two `<th>`s. `viewstate.go`'s `Tasks` field and the `?task=` query parameter
become `Tickets` and `?ticket=`, which is the last place `Task` survives in non-test code.
`CONTEXT.md` is already updated.

## Phase 1: sqlc generates store.go's queries

The phase that proves the shape. `sqlc.yaml`, the Justfile recipe, the CI job, the ADR's status
flipping to accepted, and `internal/cc/queries/store.sql` with 11 named queries.

`store.go`'s methods become mappers. `Tickets()` calls `s.q.Tickets(ctx)` and maps rows to
`[]Ticket`, keeping its `json.Unmarshal` and both error wraps. `DeleteTicket`'s
loop-over-statement-strings becomes four named queries run through `s.q.WithTx(tx)`, which is
plainer than the loop it replaces.

`putMeta` and `getMeta` become two named queries serving all eight typed accessors above them.

Smallest file, and it carries `UpsertTickets`, `ImportTickets` and `DeleteTicket`, so it exercises
transactions, upserts and the `WithTx` pattern in one go.

## Phase 2: pushes.go and refresh.go convert

Six named queries, and both latent NULL bugs.

sqlc types `events.ticket_id` as `sql.NullString` in `RestackedTickets` and
`latestRefreshOutcomes`, so both mapping sites have to state what a NULL means. It means "an event
belonging to no ticket", and both should skip the row rather than record an empty-string ticket.

`refresh.go`'s `WHERE e2.kind IN (?, ?, ?, ?, ?)` becomes `sqlc.slice('kinds')`. Written as five
positional parameters sqlc generates a params struct of `Kind`, `Kind_2`, `Kind_3`, `Kind_4` and
`Kind_5`: five interchangeable strings where swapping two compiles and returns the wrong rows.
`sqlc.slice` gives `LatestRefreshOutcomes(ctx, kinds []string)`.

## Phase 3: runs.go converts

Thirteen named queries, the largest file. Nothing here surprised the spike.

`InsertRunSkeleton` and `InsertCutFailedRun` both need `LastInsertId`, so they are `:execresult`
rather than `:exec`. The nullable columns on `runs` map onto `RunSummary`'s existing pointer
fields, which is the cleanest part of the whole migration: the pointers were already saying what
`sql.NullInt64` says.

## Phase 4: launch.go converts

Nine named queries, kept last because it holds the two shapes most likely to argue with a beta
parser, and by now the other 30 are proven.

`LaunchMemberships` carries the `COUNT(*) OVER (PARTITION BY lm.launch_id)` window function. It
generated correctly in the spike.

`CancelLaunchesFor` builds its SQL by concatenating a shared subquery string into a `COUNT` and an
`UPDATE`. Written out as two named queries, both parse and type correctly, and the shared string
disappears.

When this lands, `internal/cc` contains no SQL string literals.

## Out of scope

- **`sqlc vet`.** Query lint rules, on top of a type checker the repo does not have yet. Revisit
  once phase 4 has landed and there is something to lint.
- **`emit_interface`.** An interface with one implementation, for a store nothing mocks.
  `store_test.go` opens a real SQLite file and should carry on doing so.
- **Postgres.** Nothing in this plan assumes SQLite beyond `engine: "sqlite"` and the pinned
  driver. If the app ever needs a server database, the queries move and the mapping code does not.
